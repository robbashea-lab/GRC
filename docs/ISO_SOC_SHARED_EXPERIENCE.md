# Shared CIS, ISO 27001 and SOC 2 experience

Shared client pages reuse the approved CIS components. The dedicated ISO/SOC
program bodies, assessment engines, catalogs and saved business records remain
native. Historical `Brawndo`/`Cis` component names do not select a client or copy
its data.

## Enrollment and scope

`client_relationships.project` and the Demo `sharedProgramProjection` publish
`shared_programs` from finalized requirement records with `baseline_response =
applies`. The projection is read-only and confers no access. `sharedExperience`
also checks the existing actor, mode, authorized client list, route and loaded
identity. An empty or invalid projected enrollment cannot fall back to an
editable onboarding draft. Existing CIS assessment/command gates remain separate.

Only Dashboard, Calendar, Reviews, Actions, Risks, Policies, Vendors and AI receive
the expanded body presentation. Other client pages retain their bodies. The
shared shell marker changes header/sidebar geometry and styling; it does not
publish CIS body or portal styling onto ISO/SOC program pages.

## Framework data

`frameworkDomainProfile` uses the versioned native catalogs and
`frameworkWorkspace.hierarchyPath`. ISO groups are its ISMS clauses and Annex A
themes; SOC groups are the criteria groups in the client's configured Trust
Services Categories. Membership, assessment identities, applicability and counts
must reconcile with the canonical implementation position before rendering.
Radar and table consume the same model. Exclusions, undetermined SoA decisions,
partial work and unassessed work remain distinct; no new scoring weights exist.

Mixed clients use the existing Portfolio tab presentation to choose a separate
program posture/history through the `program` URL parameter. Risk matrix and
Priority work remain client-wide. Domain triggers retain the approved detail
popover; existing native program/status links retain their destinations.
History must match the domain source revision and status signature. A concurrent
assessment change requires refresh rather than combining different observations.

Policy mappings use native catalog mappings and explicit saved relationships.
ISO/SOC mapping failures retain verified enrollment only for labels, never for
counts. Retained mapping filters fail with an unavailable state and disable an
unknown-cohort export; existing Clear filters restores known records. Annual
review selection, version coverage, approval and recurrence commands are unchanged.

## Approved workflow exception and protected programs

The existing AI onboarding command also accepts finalized ISO/SOC enrollment.
Its fields, validation, native linked records and recovery protocol are reused.
Roles, tenant access, intake restrictions and approval-command scope remain
unchanged. Retained approvals after CIS retirement cannot cover changed deployment
or screening boundaries; those edits fail before writing. An onboarding pending
assessment is never an approval. Missing legacy metadata is not backfilled by
ordinary edits.

ISO/SOC guide changes are limited to `IsoGuidedAssessor`, `SocGuidedAssessor`, the
extracted exact `OmniGuideCharacter` artwork and locally scoped guide CSS. Native
prompts, recommendations, preferences, interview/assessment controllers and save
paths remain in place. Inline assessment interviews do not receive the new guide
wrapper. `GuidedAssessor` reuses the extracted artwork without changing CIS logic.

## Verification

Keep native controller, permission, persistence and lifecycle tests. The shared
scope, Dashboard/domain, Policy and retained AI regressions supplement them.
Run both supported builds and required Release verification on the delivered
revision. Browser evidence must distinguish actual native interactions from
source tests, Demo persistence from authenticated backend durability, and actual
browser zoom from viewport emulation. Passing CI does not establish human product
acceptance or qualify a later staging revision.
