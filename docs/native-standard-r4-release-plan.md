command, a migration authorization or evidence of acceptance.

   Reconcile the implementation ledger with actual native and visual evidence.

## Data and migration preparation

Use an authorized backup mechanism on the existing staging database only after a
separate release approval. Record its identifier, time, restoration method and
owner-controlled location without credentials or customer contents in the handoff.
Do not invent a backup or claim that a code rollback restores data.

Rehearse recovery first on a disposable synthetic database. Compare stable IDs,
original approvals and versions, completed occurrences, workers/validators,
assessment answers, evidence bytes and versions, links, indexes and audit history.
The retained R4 preservation checks are supporting evidence, not a staging backup.

R4 does not authorize a bulk reseed, implicit startup migration, replacement of
legacy assessments, historical attribution or fabricated approval identities.
Framework enrollment/reconciliation and Services/Tools changes use their native
explicit commands. Document any retained catalog or pending-command conflict by
record identity and stop that affected operation rather than silently rewriting it.

Prospective completion checks apply to a new completion. Immutable completed
occurrences remain replayable. A previously accepted annual Policy operation is
retried with its exact retained request and current authorization; no newly edited
Guide replaces that accepted operation. An unrecognized retained plan must fail
explicitly instead of being inferred or automatically migrated.

## Failure and recovery

Stop a failed admission or deployment; preserve its exact status and evidence.
Do not bypass gates, weaken assertions or start an optimization experiment.

Before restoring earlier code, assess compatibility with any newly saved R4 fields,
pending commands, framework records and file versions. Reuse the last verified
Live revision only after that assessment. An earlier build may not present new
framework or completion details even when it leaves those records intact.

If data restoration is necessary, require the authorized owner and verified backup;
identify the affected writes and preserve post-backup evidence before proceeding.
Do not drop a live database or execute an unreviewed reverse migration. Reconcile
records, attachments, history and permissions after recovery, and leave acceptance
open until the affected workflows have been retested.
