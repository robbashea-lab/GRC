# Demo reporting storage compatibility

The CIS rollout adds fictional IG2/IG3 history to the existing browser-backed Explore Demo. A regression exercising 25 native ISO scope and guided saves exhausted the existing browser quota because each changed source vector repeated unchanged reference rows.

Reporting serialization version 2 pools exact complete reference rows and stores each vector as indexes. It preserves every observation, scope, source field and native record, and restores independent copies. The reader accepts existing version 1 whole-vector strings; invalid references fail explicitly. File payload budgets, browser quota, permissions and the authenticated Mongo storage contract are unchanged.

New saves use version 2. Older application revisions cannot read that reporting format. Before reverting to an older build, preserve the current Demo state separately and plan an explicit compatible conversion; do not silently reset or reseed retained browser data. No startup or shared Mongo migration is introduced. Demo remains bounded by browser storage and file-payload limits.

Source-row pool encoding: new V2 entries store complete canonical JSON objects rather than nested JSON strings, avoiding escaping overhead. Reads retain compatibility with earlier V2 string entries and V1 string vectors. Each decoded source reference has its own nested copy, including unknown JSON fields and own `__proto__` keys. This changes serialization only; every observation, native record and history remains retained, with the original browser quota unchanged.

If the original raw JSON write raises a real WebStorage quota error, the same key is retried with lossless DEFLATE/base64 in a versioned JSON envelope using pinned `fflate` 0.8.3 (MIT). The first raw write remains unchanged; unbounded characterization fixtures therefore retain their raw serialization path. Security/unavailable-storage errors do not trigger compression. Neither retry removes the previous value first, and failed writes remain explicit failures. No history, records, unknown fields or Evidence bytes are discarded to fit.

For stores conservatively below the existing decoder bound, the quota retry first uses compression level 1. If that compressed result also hits the physical quota, it retries with the original level 6, preserving the original tighter-fit behavior. Other errors propagate immediately. Eligibility requires three times the JSON UTF-16 length to fit below the 20 MiB decoder bound with 1 MiB headroom for compression overhead; stores above that threshold use the original level 6 directly. This is an optimization threshold, not a new storage budget. Every compressed result still passes the same round-trip validation. The extra attempt can cost more when only the tighter result fits; helper benchmarks do not establish complete lifecycle performance or browser capacity.

Readers accept both legacy raw JSON and compression envelope version 1 before restoring existing V1/V2 reporting representations. The envelope records the uncompressed UTF-8 byte length; decoding validates schema/encoding/version and caps allocation at 20 MiB. This is a decoder resource bound, not a raised physical browser quota or a promise that every logical store fits. Bounded inflation reserves one extra byte and rejects a length mismatch rather than accepting truncated output. Invalid UTF-8, malformed or unsupported envelopes fail without resetting data. Diagnostics distinguish physical serialized `approximate_bytes` from `uncompressed_json_bytes`; both are UTF-16 storage-size estimates (two bytes per code unit), so they are comparable. The envelope's separate `utf8_bytes` is the actual UTF-8 decoder bound. Evidence inline/file/cache budgets remain unchanged.

Earlier application revisions cannot read a compressed envelope. Preserve the complete browser value and use a compatible reader or explicitly reviewed conversion before rollback. Never silently reset/reseed retained data. Compression provides no encryption, authenticity or new persistence backend.

Actual campaign profiling found repeated decompression of the exact same saved value. A single-entry cache now retains only the full exact validated envelope string and its immutable decoded JSON text, bounded by the existing envelope/20 MiB decoder limits. Every read still parses a fresh object; mutating returned records cannot affect later reads. Any different saved bytes must validate and decompress before replacing the cache; failed reads or writes do not replace the previously valid entry. Successful raw writes clear it. This is serialization reuse only, not a domain, authorization, navigation or multi-record cache.

Approved reporting-history redesign: referenced pool rows/vectors are validated when restoring a store, while each historical source array materializes as independent native objects only when accessed. Serialization can reuse private immutable row text for untouched history. Assignment, nested mutation after reading, deletion or descriptor replacement takes the normal current-data path; no private metadata is stored in the document. JSON serialization and native history consumers still observe expanded arrays. Scopes, continuity metadata, approvals and event order retain their existing behavior. Pools are rebuilt from reachable observations in original traversal order, avoiding accumulation of unreachable serialization rows. This changes internal loading/commit work, not the persisted format, storage provider, key, physical quota or Evidence budget. No performance qualification follows from this description; exact predecessor comparisons and original full lifecycle gates remain required.

The internal store bridge may retain one exact saved string and an immutable table of serialized source rows. Every read still decodes a fresh native store and validates referenced row/vector/scope indices; returned source arrays materialize independently. Canonical ordering is proved from normalized rows decoded from the actual saved bytes, including JavaScript numeric-index ordering and nested unknown JSON. Persisted fields cannot claim that private status. Noncanonical rows and custom prototype serialization take the established canonicalization path; prototype hooks bypass cached normalization and fast compaction. A successful changed write clears the exact-value binding by assignment, so old indices cannot authorize new data. The same immutable row table may remain solely as content proof: the next read must fetch, validate and serialize each current row before reusing a proof for its complete matching JSON text. A temporary content lookup exists for that restore only; successful complete reads replace the table, while failed reads or commits do not publish new index authority. No writer-generated row proof, native object or permission decision is cached.

The saved-string plus row-text/table size uses a conservative estimate bounded by the existing 20 MiB decoder limit. Temporary content reuse also reserves estimated space for the prior table, saved strings, lookup entries and new collector; over-cap reuse falls back to ordinary reader validation. As before, prior and replacement tables can coexist transiently during ordinary collection. This is an optimization-entry estimate, not a JavaScript peak-heap limit or new physical storage allowance. Valid data is never rejected or truncated because optimization is ineligible. The writer still performs ordinary compaction, serialization and physical commit; no whole-store reparse or fallible metadata preparation follows the physical write.

A successful compressed write also publishes its already round-trip-verified envelope and JSON text to the existing decoder text cache. The next read parses a fresh object from that exact text instead of redundantly inflating it again. Publication is limited to assignments after the physical write succeeds; failed writes retain the prior verified pair and a successful raw write clears it.

Referenced historical scope strings are also parsed eagerly once per restore when optimization is eligible. Private immutable text and comparison signatures let untouched scopes remain pooled during internal copying and compaction. The first public access to each observation's scope materializes an independent native object, preserving the original JSON text, unknown fields and per-observation enrollment order; later mutations, replacement or serialization hooks use the ordinary path. This applies to exact saved-value rereads as well as changed stores. Scope metadata shares the existing conservative optimization budget, and exhausted eligibility falls back without rejecting valid data. Optional canonicalization that reaches a stack limit also falls back to the original eager scope; required JSON parsing and reference errors still propagate. Legacy shapes and public restoration retain their established behavior. No new persistent cache, format, key, storage allowance, permission or migration is introduced.

The approved asynchronous adapter prototype first tries the same raw write. On physical quota failure, supported browsers compress with the standard `CompressionStream('deflate-raw')` API inside the existing version 1 envelope, bounded and round-trip validated by the existing decoder. Missing or unsupported format capability uses the established synchronous compressor; a native result that cannot fit retains the original level 1 and level 6 fallbacks. Runtime stream, validation and non-quota failures propagate. Input and collected output retain the 20 MiB bound; cancellation closes the streams without publishing a new value.

All ordinary Demo adapter requests queue before reading their snapshot because even some GETs can reconcile or audit data. Each request owns its body, parameters and headers before queuing or hashing can yield. Sign-out and Demo entry remain immediate and advance a document-local session generation. Native permission checks bind this owned intent to the exact authoritative stored bytes; unchanged bytes and session revalidate that decision without parsing the same store a second time. Guided requests that reread after hashing must check the same actor and all client, parent and native permission gates again before binding a new base. Every physical commit checks the generation and exact base; changed data is rejected for a fresh retry rather than replaying a mutated handler automatically. Physical storage, validated-text publication, reporting-index invalidation and Evidence cache updates complete synchronously before acknowledgment. This is same-document ordering with conflict checks, not a cross-window transaction or a rollback mechanism for an error after storage has already committed. Existing replay receipts remain in the same atomic value as their effects.

Synchronous startup, retained-data reconciliation, reset and clear APIs remain synchronous. Their writes invalidate a pending adapter save through its exact-value check. No new provider, persistent format, quota, Evidence budget, permission, migration or mutable cross-request domain cache is introduced. JSDOM tests use the actual Node standard compression implementation to exercise stream scheduling; unsupported-browser fallback tests remain explicit. Original full lifecycle and release checks still decide qualification; this design alone does not establish a timeout fix or hosted acceptance.

Guided requests may retain their own decoded snapshot across Web Crypto only when native parser/storage capabilities remain eligible, the exact authoritative saved string is unchanged, and the document-local Evidence cache revision is unchanged. The opaque cache identity changes before every cache update or clear, including updates that partially fail; it is never persisted. Any changed bytes, cache state or unsupported hook takes the existing reload path. Actor, client, authorization, trusted assessment/scope, interview revision, cancellation and exact-value commit checks remain active after either path. This removes a redundant decode within one request; it creates no shared graph cache, storage format, allowance or migration. The original uninterrupted lifecycle and release checks still decide qualification.
