This document records the narrowly necessary shared-runtime changes and the existing supported administrative workflows. It is a source-inspected operating guide, not evidence that clients were created or that hosted verification passed. The lead owns the final composite SHA, independent review, CI, staging deployment and authenticated acceptance record.

The acceptance reference is PR #62, branch `codex/omnibot-refined-workspace`, revision `83d88e3cbc31d618060c4e094335963f5bacf096`. Shared-runtime engineering occurred on `codex/omnibot-cis-runtime`; implementation and regression commits are `2685328`, `8c3792e`, `9594c15`, `1eac612`, `7318799` and `a868d98`. ## Persistence and compatibility contract

Question-stage saves persist actor-scoped interview progress only. Summary Save, Update and summary Save & close use the existing authoritative native assessment write; Save & close closes only after that write succeeds. The submitted Current Implementation value is exactly the operator-reviewed multiline string, including user edits and formatting. Submission does not regenerate it. The proposed status is a separate value. Existing attribution, explicit status handling, replacement confirmation, permission checks and history remain.

Unknown answers are not confirmed absence. Optional owner/tool/narrative/evidence context is not a mandatory source criterion. Conditional row exclusions require their source-supported condition and rationale; they do not grant whole-safeguard Not Applicable. A legitimate native N/A remains subject to the existing authorized applicability workflow. No verification or certification is inferred from interview completion.

| Safeguards | Current question version |
| --- | --- |
| 1.1 | `cis-v8.1-control1-3`, approved reference retained |
| 1.2 | `cis-v8.1-control1-4`, reviewed process, required frequency and valid response alternatives |
| 1.3–1.5 | `cis-v8.1-control1-2`, unchanged supported definitions |
| Remaining 148 unique safeguards | `cis-v8.1-program-3` |

Readers retain `brawndo-cis-pilot-1`, Control 1 v2/v3 and program v1/v2, alongside current versions. `guidedCisProgramV2.json` is the immutable archived program-v2 definition. Historical answer meanings, choices and evaluator behavior stay attached to the recorded version.

An older interview can be viewed, resumed and saved as interview progress under its recorded schema. Applying a new native assessment requires explicit current-source review. The existing UI performs a confirmed empty current-version checkpoint and, only if requested, reuses answers with demonstrated unchanged semantics. It maps stable questions/criterion identities and text and validates current per-row choices. New, changed, newly invalid or contradictory fields remain unanswered; their original values remain in history. Examples include old 1.2 `None` plus a positive response alternative, and an old 1.1 mandatory attribute marked N/A. Historical v1 mixed `gaps` text is not automatically reinterpreted as a confirmed current deficiency. Semantically unchanged optional context is retained despite scoring-metadata corrections. Manual narrative and native assessment history are not regenerated in bulk.

For a stale native/scope base, explicit comparison/rebase preserves the exact interview version, answers and reviewed wording while recording the current trusted base. A rebase cannot simultaneously restart, change answers, change narrative, complete the interview or submit a result. A later writer still needs current-version review and the existing native CAS. A comparison or version-upgrade error is shown before a write; it is not reported as assessment success.

## Supported staging showcase setup

These steps are instructions derived from source inspection. The release evidence must record actual staging client IDs, selected groups, permissions and outcomes; this document does not assert those outcomes.

1. In the authenticated existing staging application, an authorized administrator opens **Client Management** at `/admin/clients`. Its directory and client list include archived records. Record the existing IDs before making a configuration change.

Leave unknown optional industry, primary contact and GRC lead details unset; do not fabricate people or verified implementation. If Hooli exists as an unrelated client, create a different unique fictional name and report it. The form's Environment field describes client context; it does not choose a Render deployment target.
4. Use **Open Client Profile** after creation, or select the new client normally. Complete the existing four-step onboarding: **Compliance & Requirements**, **Policies & Governance Documents**, **Recurring Reviews**, **Review & Create**. Select CIS **Applies** and **CIS implementation group** IG3. Other program applicability must reflect this fictional fixture's declared scope, not change unrelated real clients. 5. 6. The normal request carries a configuration token and idempotency key. Existing assessment identities, answers, evidence, links, history and completed Reviews remain; only missing safeguards are initialized. Existing Review dates and recurrence do not automatically change. Resolve stale configuration with **Reload current scope**; use **Retry scope change** for the same interrupted submission.
7. Open the existing `/compliance/cis-ig1` route for every group; the program label and active safeguards reflect the selected configuration. Verify 56, 130 or 153 applicable placements, existing program/control entry points and native safeguard navigation. IG2/IG3 display filters do not change authorized scope. ## Compatible staging recovery

1. The lead records the current staging deployment ID/SHA, tested candidate and any new interview versions written during acceptance. Coordinate ownership of the staging slot before another deployment. This engineering document grants no independent deployment action.
2. If a critical hosted defect is found, stop further synthetic scenario writes through the affected workflow and preserve exact responses, native values, interview revisions and history. Do not report acceptance or discard new records. Existing native/manual operations may be used only where their compatibility and permissions are established.
3. Prefer a narrowly corrected forward release, or an established compatible candidate that can read every already written version and preserves current-source native-write guards, lineage/CAS protections and reviewed text. Validate that candidate against representative new and historical checkpoints before the lead uses the normal existing staging workflow.
4. Do **not** blindly roll back to the original 1.1 pilot or an older writer. It may not read program-v3/Control-1-v4 interviews, may reject the explicit rebase command, or may apply the historical rules this rollout corrected. Deployment rollback does not undo data writes. Do not change version labels, downgrade catalogs, reset interviews, regenerate native assessments, reduce group scope or restore a database as a shortcut.
5. Reload hosted browser sessions after the compatible deployment and rerun affected lifecycle/isolation/serialization checks against its actual SHA. Preserve all newly written interviews and native history. If no safe compatible candidate is available, the lead records a release blocker and exact required correction rather than using an incompatible writer.

No migration is required to activate this runtime. Compatibility is additive and explicit; it does not assert that all historical interview snapshots already exist. The history API describes retained snapshots, not reconstructed missing history.
