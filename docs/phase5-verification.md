# Phase 5 verification: onboarding to operational handoff

## Implementation and inspected lifecycle

The existing v3 four-step flow is retained: Compliance & Requirements, Policies & Governance Documents, Recurring Reviews, Review & Create. Compliance intentionally comes first because its CIS configuration supplies the following steps. The pre-change inventory is in [phase5-onboarding.md](phase5-onboarding.md).

Finalization continues to create or retain 17 baseline Policies, six existing catalog applicability records, selected general Reviews, and applicable CIS assessments/mapped Reviews. The tested default CIS configuration produces 12 Reviews and 56 assessments. Generic Reviews are optional. No People, accounts, Findings or Action Items are generated by this four-step flow. Existing generation, recurrence, scheduling, assignment and lifecycle rules are unchanged.

Previously, Policy omissions surfaced only at finalization, Unsure applicability lacked a visible input, completion redirected to a framework or Dashboard, and the completed route remained an editable wizard.

The implemented changes are:

- Early Policy answered/required counts and inline omissions, with focus on the first unanswered response. Unsure is valid. Existing server validation remains. Invalid custom cadence configuration is explained before leaving Reviews; owners and dates remain optional.
- Explicit Applies / Does Not Apply / Unsure program selection using the existing values.
- Review & Create previews create versus retain counts, Policy response distribution, configured programs, Review scheduling/ownership, and authoritative Primary Contact/GRC Lead context. Existing matching/deduplication rules are reused; no readiness percentage is invented.
- Completion stays on a compact operational handoff. Revisiting shows current setup and an expandable read-only saved baseline, not an editable wizard.
- Client creation offers a Continue onboarding action. An incomplete client's Dashboard gets a small setup notice; completed clients retain the operational Dashboard with a handoff link. Management metric calculations are unchanged.
- Existing Client Settings gains a focused program-applicability control, allowing later program additions/removals without replaying Policy intake. CIS uses the existing reconciler unchanged. Other programs remain honest placeholders, not fabricated assessments.
- The separately approved Findings correction guards two record-dependent validation sections when no Finding is loaded. This repairs the reproduced standalone Findings-page crash without changing workflow or lifecycle.

## Current counts and authoritative navigation

| Handoff area | Calculation | Destination |
| --- | --- | --- |
| Review scheduling | Active Reviews whose existing occurrence view is Needs Scheduling; completed/cancelled excluded | Reviews with a removable setup filter |
| Review ownership | Active Reviews with no stored owner | Reviews with an ownership setup filter; existing Phase 4B picker |
| Policy follow-up | Non-retired Reported Missing, or Reported Existing / Needs Confirmation, respectively | Policies with the matching removable setup filter |
| People | Authoritative Primary Contact and GRC Lead, business Contact count, active client User count, availability from the existing eligible-assignee query | Contacts & Roles and authorized Client Management |
| Compliance | Current structured applicability records; actual CIS assessment totals and Not Assessed states | Existing client-specific framework page and program configuration |

The summary and register setup links share predicates. Search and additional column filters remain available; entering a handoff link clears stale saved table filters so the initial rows match the linked setup count. Users can remove the setup filter normally.

Counts are derived on load/revisit from current operational records, including records added after onboarding. No duplicate mutable counters, tickets or setup records are stored. Scheduling/assigning a Review, verifying a Policy or starting a CIS assessment updates the next handoff read. Reported existence is not verification. Zero client Users is informational when eligible internal staff can own work. Contacts are not made assignable and neither Primary Contact nor GRC Lead is automatically assigned to Reviews.

The saved intake is distinct from current operations. Operational changes and the new program adjustment path leave it unchanged. The historical baseline API remains mutable for compatibility; the read-only completed UI is not a new immutable audit-history guarantee. Removing a program changes current applicability/navigation without deleting assessments or operational history.

## UI, accessibility and performance review

The better-ui and emil-design-eng guidance was used to keep the approved light workspace, charcoal sidebar, neutral surfaces, compact hierarchy and existing controls. No new palette, navigation system or animation was introduced.

| Severity | Location | Before | After | Why |
| --- | --- | --- | --- | --- |
| Medium | Policy step | Omissions discovered at the final step | Inline counts, text feedback and first-omission focus | Make the required next action clear without relying on color |
| Medium | Completion | Abrupt redirect into a framework | Four compact live setup panels with specific links | Explain what remains while keeping work in authoritative modules |
| Low | Client creation / Dashboard | Next step or empty-program meaning unclear | Contextual onboarding action and small setup notice | Distinguish incomplete setup from a mature quiet program |
| Medium | Standalone Findings | Closed validation content dereferenced a missing record | Record-dependent content rendered only when loaded | Preserve page rendering and normal validation behavior |

**Review disposition: Approve the inspected changes.** The handoff screenshot was visually inspected. Browser checks covered readable labels/counts, required-field focus, existing selector keyboard/Escape behavior and responsive widths. Native buttons/selects/links/details and existing design tokens are reused. Full screen-reader testing, a whole-application WCAG audit and 10% slow-motion animation inspection were not performed; no new animations were added.

One authorized handoff request consolidates four bounded, client-scoped projected collection reads plus aggregate People counts and the existing scoped assignee-availability query. There is no per-record user lookup or frontend platform-directory fetch. Each operational collection has a 2,000-row cap and fails explicitly above it instead of silently returning inaccurate counts. Large-client pagination/server aggregation beyond that cap is not implemented. No latency improvement or scale benchmark is claimed.

## Security, integrity and remaining limitations

Code review and automated authorization checks confirm that the new read/write routes use existing authenticated client access and write-role checks. Program writes accept only existing catalog keys and tri-state applicability, reject extra fields, and audit changes. Reads have minimal projections and do not mutate data. No RBAC, memberships, assignment eligibility, account creation, approval authority, authentication, recurrence, framework mappings, metric definitions or operational lifecycles were changed.

Final diff/whitespace and targeted secret-pattern checks found no introduced credential material, environment files/values, dependency changes, build artifacts or debugging scripts in the tracked change. Temporary browser fixtures/screenshots/scripts and the deployment archive remain outside Git. This is a scoped scan and self-review, not independent security assurance.

**Not verified:** a persistent MongoDB/staging backend, standard authenticated browser operation, real invitation delivery and deployed backend operation. Backend verification used isolated in-memory persistence; Demo browser mutations remained session-isolated. The frontend release must not be described as enabling standard authentication or proving production readiness.

No additional product decision is required for this scoped handoff. Intentional limits are preserved: optional ownership/schedules, no automatic remediation/account creation, placeholder frameworks without fake percentages, no replay of completed intake in the UI, and refresh/revisit-based current counts rather than real-time push updates. Legacy six-step callers and mutable baseline compatibility remain unchanged.

Source commit, GitHub mirror and published version are reported in the release handoff after they are confirmed. The published frontend artifact must be the final browser-tested build identified above; publishing it does not deploy the backend.
