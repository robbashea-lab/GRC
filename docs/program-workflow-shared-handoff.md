## Ranking and source contract

Internal tiers are urgent 4, high 3, neutral/standard 2, routine 1. They are application triage defaults, not official framework criticality or measured client risk. Discovery sorts reviewed dependency layer, reviewed inherent importance, then stable requirement ID. Assessed remediation sorts the highest precise unresolved gap priority, native Not Implemented / Partial / Implemented-with-gap tie order, exact linked deadline, then stable ID. Multiple gaps and records receive no extra votes and no averaging. An absent/partial native assessment remains actionable after checklist resolution or Finding closure until a real accepted reassessment changes it.

Only an open native Item of kind gap establishes an Implemented-with-gap remediation slot. Optional SOC/ISO legacy prose is insufficient affirmative intent; verification Items and broad evidence/Review Findings remain separate. Exact linkage requires authorized client, assessment ID, Item ID, and Finding ID. The workspace scalar projection adds these identities, associated child Finding IDs/deadlines, and native assessed Risk levels from the Finding's same-client risk link. All source reads remain bounded at the existing 10,000-record boundary and one bulk Risk read; no per-requirement network/database query or new capture formula was added. Counts and denominators are unchanged.

Existing scales normalize for ranking only: critical/immediate 4, high 3, medium/moderate 2, low 1; unsupported ratings supply no severity. Exact linked Finding/Risk severity precedes reviewed ID/question/criterion defaults. Actual unresolved matrix rows select their exact authored row or stable criterion mapping. Missing precise mappings use neutral 2 and remain exposed in internal `triage.unmapped`; a native position without structured gap provenance also has an explicit neutral fallback.

The inspected native model has no approved gap-priority field or approval provenance. An Action priority commonly inherits Finding severity, so it is not silently treated as approved client override. This precedence branch remains unavailable until an authoritative supported approval contract exists; no new priority field, customer rating, permission, or UI was invented.

The existing remediation model retains multiple child tasks. Completion of all required child work produces Pending Validation (`remediated`); authorized validation closes the Finding; reopening retains completed actions/history. Item resolution, Finding closure, risk acceptance, and child completion do not revise native implementation or independent verification. Existing route suites passed; no speculative lifecycle-service rewrite was made.
